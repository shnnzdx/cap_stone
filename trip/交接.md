## 三、关键决策与理由

这一节记的是**为什么这么定**。改之前先看一眼,否则很容易把已经想清楚的坑再踩一遍。

### D1 · 判定不用 AI,用死规则

大模型同一个问题问两次可能给不同答案。一个以"公平"为卖点的产品,规则本身不能是飘的;
而且每改一次行程都调一次 AI,又慢又贵。

**AI 只在用户写下约束的那一刻出场**:把人话翻译成六种类型之一 → 用户确认 → 存下来。
以后判定只看存下来的规则,再也不问 AI。既保留自由输入,又保证判定确定。

守这条的测试:`test_same_input_always_gives_same_answer`

### D2 · 约束只有六种类型,不是自由文本

原契约里 `EssentialNeed.text` 是一句话,前端靠正则去 parse 小时。撑不到真后端。
现在拆成六种可判定的类型(见 `BACKEND.md` 第三节)。

**代价必须接受**:填不进这六种的约束,系统会诚实地说"这条我保护不了,请写进公开说明"
—— 而不是假装保护了。

### D3 · 隐私靠结构,不靠"记得过滤"

三层:数据库两张表、类型上装不下、通知表没有 actor 字段。
详见 `BACKEND.md` 第二节。

**为什么不在 API 层过滤**:每写一个新接口就要记得过滤一次,迟早漏。
现在是想漏也没地方装。

守这条的测试:`test_findings_never_carry_identity_or_wording`

### D4 · 加了第四条路:重开轮

原设计里 `settled` 的时段"单个人不足以重开,需多人联署"——**但联署机制在 UI 里从来不存在**,
而且它要求私下拉票,恰恰是本产品要消灭的行为。

**曾考虑让它走 Confirm,否决了**:Confirm 要全票且没有截止时间,
一个全组投票定过的时段"相关的人"是全组六个,只要一个人在忙就永远改不动——比原方案更僵。

改成:**重开一轮投票,但门槛更高**(要写理由 + 要过半数明确支持)。
有截止时间、按票数落地、并行一键,是处理"争议"的正确工具。

### D5 · 沉默的含义按路径分档

- 首次决定:没投票 = 中性,不影响结果
- 重开推翻已定的事:没投票 = **算在"维持原样"这边**

懒得理的人显然不觉得这事需要改。

守这条的测试:`test_silence_is_never_counted_as_agreement`、
`test_a_minority_cannot_overturn_a_settled_decision`

### D6 · 行程用流水账,不直接 UPDATE

`plan_change` 只追加。一个条目"现在长什么样"= 原始状态叠加所有改动。
免费得到版本号、"谁改的为什么"、可回滚。

**答辩时把 `GET /api/plans/{id}/changes` 摊开就是决策全过程。**

### D7 · 关键不变量下沉到数据库

"一个条目同时只能有一轮开着的投票"这类规则,用部分唯一索引强制,不靠应用层记得检查。
应用层再拦一道给用户一句人话(409)。**两道都要:应用层管体验,数据库管正确。**

这条在开发中救了一次——演示时真撞到了,数据库拦住了,当时接口返回 500,现在返回 409。

### D8 · 身份先用假的

请求头 `X-Membership-Id` 说自己是谁。**真做登录时只改 `current_membership()` 一个函数。**
先不做登录是为了不让它挡住核心流程;这个决定不会产生返工。

### 明确删掉的东西

- **Lock / Final 发布 / 满意度评分 / 三种锁定模式** —— 以 trip demo 为准,老提案那套整块不建
- **多人联署** —— 见 D4
- **"弃权"记录** —— 沉默就是没有记录。存成一条记录,早晚有人把它当成一种表态

## 四、怎么接你的 AI Agent

**你不需要任何新通道。Agent 用的是人也在用的那两道门。**

### 门一 · 提交行程改动 ✅ 已经能用

```http
POST /api/plans/items/{item_id}/changes
X-Membership-Id: <给 AI 建一个 membership>

{ "title": "...", "start_hour": 15.5, "lat": 41.88, "lng": -87.62,
  "request": "为什么要改", "reason": "重开时必填" }
```

返回里 `path` 告诉你后端把它判成了哪条路:

| path | 意味着 | `applied` |
|---|---|---|
| `notice` | **当场就改了** | `true` |
| `round` / `reopen_round` | 开了一轮投票,行程没变 | `false` |
| `confirm` | 建了一个待确认,行程没变 | `false` |

**所以"AI 能不能直接改行程"的答案是:能,但只在 `notice` 那种情况下,
而且这不是 AI 的特权——是规则允许的。** 撞到硬底线时它一样改不动,
一样不能替别人同意。AI 有 bug 时能造成的最大破坏,也就是改了一个没人在乎的时段,
而且全组都收到通知,谁不同意点一下就翻案。

### 门二 · 试算(不执行)✅ 已经能用

```http
POST /api/plans/items/{item_id}/classify
```

**同一个 body、同一套判定,跑完回滚。** 所以试算和真做永远不会不一致。

**不花钱、不慢**(判定不调 AI),可以随便试。私聊里的引导就靠它:

> **用户**:周二下午我想去购物
> **AI**(试算)→ 得到 `round` + "这个时段已经有人碰过"
> **AI**:这会开一轮全员投票,不是直接生效。换成下午 3 点之后就能直接生效,要试试吗?

### 门三 · 写用户的约束 ⬜ 还没做

AI 翻译那一步的落点。**这是唯一还缺的门**,是接 agent 前必须先补的:

```
PUT  /api/trips/{id}/preferences/me
POST /api/trips/{id}/constraints          写一条六种类型之一
GET  /api/trips/{id}/constraints/me       只能看自己的
```

表已经有了(`member_constraint` + `member_constraint_private`),缺接口。

### AI 的五个活

| 活 | 输入 | 输出 | 落地方式 |
|---|---|---|---|
| **翻译约束** | 用户随口一句话 | 六种类型之一 + params | **必须用户确认**才写库 |
| **生成行程** | 匿名约束集 + 景点库 | `PlanItem[]` | 过规则检查,失败重生成一次,仍失败标 `blocked` |
| **解释** | 行程 + `AnonymizedFinding` | Why this works / Trade-offs / 可信度标签 | 只读,不改行程 |
| **出候选项** | 被争夺的时段 | 3 个选项(**必须含「分头行动」**) | 交给 Round |
| **私聊** | 本人偏好 + 公共行程 + 匿名群体约束 | 对话 | 想改就走门一 |

### 四条红线

1. **AI 的上下文里永远不含别人的私密原文。** 只给 `AnonymizedFinding`
   (`code` + `safe_text` + `affected_count`)。
   这同时解决隐私和 prompt injection ——prompt 里根本没有私密数据,套也套不出来。
2. **生成的行程必须过规则检查才能上线。** 不得展示一份看起来正常但实际违规的行程。
3. **可信度标签由代码打,不由 AI 自称。** 景点来自策展库 = `verified`,
   AI 编的价格时长 = `ai_estimate`。让模型自己标等于没标。
4. **AI 自动改动要署名,不能匿名。** 匿名是为了保护人,AI 不需要保护,
   而且用户有权知道这是机器改的。通知写 `TripSync adjusted this`,不写 `a member`。

### 装个刹车

AI 自动改动要有上限:同一个条目不能连着改、一轮不能改超过 2–3 条。
不然哪天出 bug,它会疯狂重排整个行程。

### 什么时候 AI 会自己动(真正的 agent 行为)

| 触发 | AI 干什么 |
|---|---|
| 用户在私聊里说想改 | 试算 → 问要不要提交 |
| **有人更新了偏好,和现有行程冲突** | 自己算出修复方案 → 自己提交 |
| **投票刚定了新方案,把后面几天搞乱了** | 自己修连锁影响 |

后两种天然落在 `notice` 上(在修复冲突,不是在抢时段),所以真的会当场生效。

## 五、还剩什么

按建议顺序。⭐ = 答辩必须有。

| # | 事情 | 卡在什么上 |
|---|---|---|
| 1 ⭐ | 偏好接口 + 六种约束增删改 | 无,随时可做。**接 AI 之前必须先有** |
| 2 ⭐ | AI 五个活 | 你的 `OPENAI_API_KEY` |
| 3 ⭐ | 景点库 40–50 个 Chicago 景点 | 需要人整理(AI 生成 + 人工抽查,约半小时) |
| 4 ⭐ | 前端接后端 | 无。**最容易被低估的一块** |
| 5 | 组织者功能 + 僵局出口 | 无 |
| 6 | 登录 / 邀请链接 / Guest | 要不要做 |
| 7 | 重开轮 48 小时冷却期 | 无,半天 |
| 8 | Trip 四状态自动流转 | 无 |

**可以砍掉且答辩看不出来的**:6、8,以及组织者功能里除僵局出口之外的部分。

### 景点库的字段(做第 3 项时用)

每个景点必须有:`name` `place` `lat` `lng` `price_estimate` `duration_min`
`opens_at` `closes_at` `walk_difficulty` `accessibility_flags` `dietary_flags` `tags`

**后四个字段不能省。** 用户填的约束(走路距离、无障碍、饮食),
只有在景点资料里有对应那一栏,程序才判断得出来。没有就是摆设。

## 六、已知的坑

| 坑 | 说明 |
|---|---|
| **6 人小组的匿名是脆的** | "有一条时间要求不能早于 9 点"可能一猜就中。对外别说"完全匿名" |
| `seed.py` 会删表 | `python -m app.db.seed` 先 drop 再 create,只在开发时用 |
| 没有 Alembic | 现在靠 `create_all`。表结构一稳定就该加迁移工具,否则改字段要删库 |
| 定时任务跟着后端进程跑 | 部署时**不能用 Vercel 那种"有人访问才醒"的服务**。用 Railway / Render 这类常驻的 |
| `trip_total_after` 由调用方传 | 引擎保持纯函数,不自己算总价。接偏好接口时记得把它算对,否则预算上限判定会失效 |
| `test_paths.py` 里有几条守的是产品承诺 | 改它们之前先确认产品真的改了主意,不要为了让测试过而改测试 |
| 两份 demo 副本 | `Documents/trip/tripsync_living_demo` 和 `Desktop/.../trip` 是同一个前端的两份。**后端只在 Desktop 这份里** |
