# 多人协作式 AI 旅行规划平台
## 首页核心动画设计稿 V3

**文档状态：** 概念设计阶段  
**设计范围：** 首页 Hero 区域中的左侧 3D 球形想法模型、中间处理区域占位、右侧计划生成流程  
**主题色：** 淡蓝色  
**核心叙事：**

> 分散且持续产生的个人想法，被平台吸收和协调，最终逐步形成一份结构化的共同旅行计划。

---

## 1. 设计目标

这个动画不是普通的数据流示意图，也不是静态背景装饰。它需要在用户进入首页后的几秒内，直观表达产品的三个核心价值：

1. 多名成员会不断产生独立、分散且性质不同的旅行想法。
2. 平台会吸收、理解和协调这些想法。
3. 旅行计划不是一次性突然生成，而是逐项、逐层构建完成。

整体视觉故事为：

```text
3D 球形想法集合
    ↓
持续吸收与处理
    ↓
结构化计划逐步形成
```

---

## 2. 整体画面结构

桌面端采用横向三段式布局：

```text
┌──────────────────┬──────────────────┬──────────────────┐
│                  │                  │                  │
│   左侧 3D 想法球  │   中间产品处理区   │   右侧计划生成区   │
│                  │                  │                  │
│  独立点持续生成    │   概念暂时保留     │   自上而下点亮     │
│  Hover 显示想法   │   仅保留接口位置   │   逐步形成 Plan    │
│  粒子被吸入中心    │                  │                  │
│                  │                  │                  │
└──────────────────┴──────────────────┴──────────────────┘
```

建议视觉占比：

- 左侧：38%
- 中间：24%
- 右侧：38%

左侧需要足够空间建立真正的 3D 深度；中间暂时只承担视觉汇聚中心；右侧需要完整展示纵向计划形成过程。

# 3. 左侧：3D Collaborative Idea Sphere

## 3.1 核心定义

左侧不是一张静态图片、二维粒子背景或普通的规则点阵球。

它是一个持续运行的 **3D 协作想法球（3D Collaborative Idea Sphere）**：

- 球体由大量独立粒子共同构成。
- 每一个粒子代表一条独立的成员想法、偏好、限制或顾虑。
- 每个粒子拥有自己的三维坐标、大小、透明度、运动状态和标签内容。
- 球体整体缓慢旋转，但单个粒子仍存在轻微的局部漂移。
- 系统持续生成新的粒子。
- 部分现有粒子会被提取并沿曲线路径进入中间平台。
- 粒子一边产生、一边流出，球体的整体体积和密度始终保持稳定。
- 每个可交互粒子都支持鼠标悬停并显示对应想法。
- 标签不会始终显示，系统只会每隔 2–3 秒自动展示 1–3 个标签。

该模型表达的是：

> 多位成员不断产生彼此独立的旅行想法。这些想法共同形成当前旅行小组的需求集合，但在进入平台前仍然是分散、无序且尚未协调的。

---

## 3.2 视觉参考与原创转换原则

该模型可以学习 Auros 网站球形 3D 设计中的以下视觉机制：

- 大量独立微粒共同形成一个清晰的球形轮廓。
- 球体具有真实厚度，而不是只有一层球面。
- 外围粒子较密，中心区域更暗、更稀疏。
- 前景与后景粒子通过尺寸、亮度和透明度形成深度。
- 整体缓慢旋转，局部粒子又存在轻微独立运动。
- 球体看起来像一个持续流动的信息生命体，而不是刚性几何物体。

本项目不复制其具体素材、字符、着色器或源代码，而是将这种视觉机制转换为项目自身的产品语义：

```text
参考模型中的数据粒子
            ↓
本项目中的成员想法与旅行约束
```

最终模型必须具备独立的品牌颜色、交互方式、标签系统和粒子流出逻辑。

---

## 3.3 球体不是规则实心球

球体应保持明确的整体轮廓，但不能将粒子平均铺在一个完美球面上。

推荐形态：

- 基础轮廓接近球形，允许轻微椭球变化。
- 粒子分布使用随机噪声，避免规则网格感。
- 球壳具有明显厚度。
- 局部区域可以较密，局部区域可以较疏。
- 球体中心区域相对空旷和暗淡。
- 轮廓边缘相对更密、更亮。
- 用户能够透过前景粒子看到较暗的后方粒子。
- 部分粒子位于球体内部，而不是全部贴在球面上。

视觉结构可分为三层：

### 外层粒子

- 构成球体主要轮廓。
- 数量最多。
- 边缘对比度较高。
- 最容易被用户观察和交互。

### 中层粒子

- 增加球体厚度和体积感。
- 透明度和尺寸适中。
- 与外层共同形成流动结构。

### 内层粒子

- 数量较少。
- 透明度更低。
- 主要负责表现内部空间。
- 不应将球体填成实心。

整体效果应是：

```text
清楚看出它是一个球
+
清楚感受到内部仍然存在空间和流动
```

---

## 3.4 单个粒子的数据模型

每个粒子都应是独立的数据实体，而不是仅用于装饰的随机像素。

建议的数据结构：

```ts
interface IdeaParticle {
  id: string
  ideaText: string
  memberId?: string
  category: IdeaCategory
  priority: "constraint" | "strong_preference" | "preference" | "optional"
  visibility: "public" | "private"
  position: { x: number; y: number; z: number }
  basePosition: { x: number; y: number; z: number }
  velocity: { x: number; y: number; z: number }
  radiusOffset: number
  size: number
  opacity: number
  brightness: number
  depth: number
  state: ParticleState
  lastFeaturedAt?: number
}
```

粒子状态：

```ts
type ParticleState =
  | "spawning"
  | "floating"
  | "featured"
  | "hovered"
  | "selected"
  | "detaching"
  | "exiting"
  | "absorbed"
```

状态含义：

- `spawning`：新想法正在进入球体。
- `floating`：粒子正常参与球体运动。
- `featured`：系统自动展示该想法。
- `hovered`：用户当前正在查看该粒子。
- `selected`：粒子已被系统选择，准备进入中间平台。
- `detaching`：粒子正在脱离球体运动体系。
- `exiting`：粒子正在沿曲线路径移动。
- `absorbed`：粒子已进入中间区域并从左侧场景移除。

---

## 3.5 粒子的形态

为了保持项目的柔和旅行产品气质，基础粒子不需要全部使用数字或字符。

建议采用混合形态：

### 主要粒子

- 小型圆点。
- 柔和的淡蓝色。
- 边缘有非常轻的光晕。
- 数量最多。

### 强调粒子

- 小球、细小方块或短片状碎片。
- 尺寸略大。
- 用于可交互想法和自动标签展示。
- 不能多到破坏球体统一性。

### 背景微粒

- 尺寸非常小。
- 低透明度。
- 主要形成体积和空气感。
- 不承担 Hover 交互。

所有可见粒子在产品语义上都代表想法，但在技术实现中可以将真正需要交互的粒子划分为一个较小的实例集合，以控制性能。

---

## 3.6 球体的三层运动

球体需要同时具备整体运动、单点运动和粒子生命周期运动。

### 第一层：整体缓慢旋转

球体持续缓慢旋转，让用户能够看到前后深度。

建议：

- 主要旋转方向为水平方向。
- 垂直方向只有非常轻微的摆动。
- 旋转速度不是完全固定，可以轻微缓入缓出。
- 不应快速旋转。
- 不应出现突然改变方向的动作。

推荐感受：

```text
稳定、缓慢、持续
```

而不是：

```text
炫技、快速、机械
```

---

### 第二层：单个粒子的局部漂移

单个粒子不能完全锁死在球体表面。

每个粒子可以具有：

- 轻微上下漂移。
- 轻微左右偏移。
- 非常小的径向变化。
- 柔和的亮度变化。
- 不同的噪声相位和速度。

这样即使整体球体没有明显旋转，局部仍然像一个活跃的信息体。

粒子的局部运动幅度必须很小，不能让球体轮廓失去稳定性。

---

### 第三层：粒子持续生成和流出

粒子的完整生命周期为：

```text
新想法产生
→ 淡入球体
→ 加入球体运动
→ 可能被自动展示或 Hover
→ 被系统选择
→ 脱离球体
→ 沿曲线路径进入中间平台
→ 在其他区域补充新粒子
```

三层运动应同时发生：

- 球体整体在慢慢旋转。
- 单个粒子在球壳中轻微漂移。
- 少量粒子正在进入或离开球体。

---

## 3.7 自动标签展示机制

标签不是球体表面的固定元素。

系统每隔约 2–3 秒自动选择 1–3 个当前可见粒子，并短暂展示其想法。

推荐时间范围：

```text
出现间隔：2.3–3.2 秒
同时展示：1–3 个标签
淡入：200–300ms
稳定展示：1.8–2.3 秒
淡出：200–300ms
```

自动标签选择规则：

- 只选择位于球体正面或侧前方的粒子。
- 不选择严重被遮挡的粒子。
- 不选择正在离开球体的粒子。
- 不选择正在被 Hover 的粒子。
- 同一个粒子短时间内不能重复出现。
- 同一组标签尽量来自不同位置和类别。
- 同时出现的标签不能互相遮挡。
- 标签总数最多为 3 个。
- 在视觉空间较小时，自动降为 1–2 个。

自动标签示例：

- “Budget under $1,200”
- “Prefer a late start”
- “Vegetarian options”
- “Walk less”
- “Near public transit”
- “Would love a museum”
- “Need a quiet room”
- “Private concern”

私密需求的自动标签只显示抽象概括，例如：

```text
Private concern
Personal constraint
Accessibility need
```

不能自动展示具体的敏感信息。

---

## 3.8 鼠标悬停交互

用户可以将鼠标悬停在可交互粒子上，查看该粒子代表的想法。

Hover 后：

1. 粒子轻微放大。
2. 粒子亮度增加。
3. 对应标签立即出现。
4. 标签通过短线或视觉锚点与粒子关联。
5. 周围粒子轻微降低透明度。
6. 当前粒子的局部漂移暂时停止。
7. 整个球体仍继续缓慢运动。
8. 当前粒子在交互过程中不能被系统吸走。
9. 鼠标移开后，标签在约 200–300ms 内淡出。

Hover 标签拥有最高优先级：

```text
Hover 标签
    >
系统自动展示标签
    >
普通粒子状态
```

当 Hover 发生时：

- 系统可以暂时减少自动标签数量。
- 当前 Hover 标签必须保持稳定。
- 即使球体继续旋转，也应短暂锁定当前粒子的可视位置。
- 不允许标签因为深度排序而频繁闪烁。

---

## 3.9 标签气泡样式

标签使用轻量级玻璃拟态，不使用大面积实心卡片。

结构示意：

```text
┌────────────────────────────┐
│  图标   想法文本            │
└────────────────────────────┘
```

建议样式：

- 背景：半透明白色或极浅蓝白。
- 边框：1px 淡蓝灰。
- 圆角：10–14px。
- 阴影：轻微。
- 模糊：适度 backdrop blur。
- 字体大小：12–14px。
- 文本最多一行或两行。
- 标签始终面向屏幕。
- 标签不跟随球体自身角度旋转。
- 标签根据粒子的屏幕投影位置自动调整方向。
- 标签不得超出 Hero 区域边界。

---

## 3.10 鼠标视差与相机运动

为了增强三维深度，可以加入非常克制的鼠标视差。

鼠标在 Hero 区域移动时：

- 相机视角轻微偏转。
- 前景与后景粒子产生不同程度的位移。
- 球体整体仍保持稳定。
- 标签始终面向屏幕。

建议最大幅度：

```text
水平偏转：±4°
垂直偏转：±2.5°
```

用户没有移动鼠标时，球体仍然保持：

- 缓慢自动旋转。
- 轻微的呼吸式变化。
- 单个粒子的局部漂移。

---

## 3.11 新粒子的持续生成

新粒子不是从一个固定入口进入，而是在球体多个区域自然出现。

主要生成区域：

- 球体左侧边缘。
- 球体后方。
- 上方和下方外围。
- 少量从球体内部深处淡入。

生成过程：

```text
透明度 0
→ 极小尺寸
→ 缓慢淡入
→ 达到正常尺寸
→ 加入 floating 状态
```

推荐生成时间：

```text
600–1,000ms
```

生成规则：

- 新粒子不能密集出现在同一个区域。
- 大部分新粒子不需要发光。
- 少量新粒子可以短暂增强亮度，表达“新的想法出现”。
- 生成速度需要与流出速度保持大致平衡。

---

## 3.12 粒子从球体脱离

进入中间平台的粒子应优先从球体右侧或右前侧离开。

每批建议选择：

```text
1–4 个粒子
```

选择条件：

- 当前没有被 Hover。
- 当前没有正在显示标签。
- 位于右侧半球。
- 靠近球体外层。
- 最近没有参与过展示。
- 离开后不会在球体表面造成明显空洞。

脱离过程分为三步。

### 第一步：被选择

```text
floating → selected
```

表现：

- 亮度轻微提高。
- 局部运动速度降低。
- 运动方向开始偏向球体外侧。

### 第二步：脱离球体运动体系

```text
selected → detaching
```

表现：

- 粒子不再完全跟随球体旋转。
- 与球体表面逐渐拉开距离。
- 球体其他粒子继续正常运动。
- 用户能够看出该粒子正在被提取。

### 第三步：进入曲线路径

```text
detaching → exiting
```

表现：

- 粒子接入 3D spline。
- 速度逐渐增加。
- 后方出现极短的淡蓝光迹。
- 光迹随后消失。
- 粒子向中间区域收束。

---

## 3.13 曲线路径设计

球体到中间平台之间可以存在 3–6 条隐藏的主 spline。

路径规则：

- 平时不显示完整轨道。
- 只有粒子经过时才出现局部光迹。
- 光迹透明度从粒子附近向后逐渐衰减。
- 不同路径具有轻微的高度和深度差异。
- 路径不能互相平行。
- 路径不能出现尖角。
- 接近中间区域时逐渐收束。
- 粒子速度采用缓入缓出。
- 同一时刻不要有大量粒子沿所有路径移动。

这种方式可以保留球体的纯净感，同时清楚表达想法正在被平台吸收。

---

## 3.14 动态平衡机制

球体不能随着粒子流出而逐渐变空。

系统应维护目标粒子数量和密度。

建议数量范围：

```text
高性能桌面端：3,000–15,000 个视觉粒子
普通桌面端：1,500–6,000 个视觉粒子
平板端：600–2,000 个视觉粒子
移动端：250–800 个视觉粒子
```

其中真正参与 Hover 的交互粒子可以远少于总视觉粒子，例如：

```text
桌面端可交互粒子：100–300 个
移动端可点击粒子：30–80 个
```

动态平衡规则：

- 每移除一个交互粒子，系统在其他区域补充一个新想法粒子。
- 背景微粒可以通过循环缓冲池重复使用。
- 新粒子主要补充在左侧、后方和上下外围。
- 球体总体半径和视觉密度不发生明显变化。
- 任何时候都不能出现右侧区域被持续吸空的缺口。

---

## 3.15 颜色与材质

项目主题色为淡蓝，不能直接复制深色背景上的高亮青绿色效果。

推荐背景：

```text
左上：#FBFDFF
中心：#F5F9FF
右下：#EEF6FF
```

推荐粒子层级：

```text
普通粒子：#C7DCFA
中层粒子：#AFCDF7
活跃粒子：#82B5F5
高亮粒子：#5F9EF1
后景粒子：低透明度灰蓝
```

浅色背景下的渲染原则：

- 主要使用普通透明混合。
- 少量高亮粒子可以使用轻微加色效果。
- 不依赖过强 bloom。
- 球体边缘通过密度、深度和对比度强化。
- 球体中心通过降低密度和亮度保持空间感。
- 后景粒子应更暗、更透明。
- 不能让整个球变成发白的光团。

---

## 3.16 技术实现建议

建议采用 WebGL，而不是为每个粒子创建独立 DOM。

推荐结构：

```text
React / Next.js
└── React Three Fiber / Three.js
    ├── Visual Particle Sphere
    ├── Interactive Idea Instances
    ├── Custom Shader Material
    ├── Particle Lifecycle Manager
    ├── Hover Picking
    ├── Auto Label Manager
    ├── Exit Particle Pool
    ├── Spline Animation
    └── Camera Parallax
```

推荐混合渲染方案：

### 大量视觉粒子

使用：

- `THREE.Points`
- 自定义 Vertex Shader
- GPU 噪声和径向运动
- BufferGeometry

作用：

- 形成球体主体。
- 支撑数千到数万粒子。
- 提供整体体积和流动感。

### 可交互想法粒子

使用：

- `InstancedMesh`
- 独立 instance ID
- 独立想法数据映射
- Raycasting 或 GPU Picking

作用：

- 支持 Hover。
- 支持自动标签。
- 支持单点高亮。
- 支持粒子脱离和进入中间平台。

在产品语义上，所有点都代表想法；在底层实现上，通过视觉层和交互层分离保证性能。

---

## 3.17 Hover 检测建议

粒子数量较多时，不应对所有视觉粒子逐个执行复杂碰撞检测。

可采用：

- 只对交互粒子执行 Raycasting。
- 使用实例 ID 找到对应想法。
- 将交互粒子限制在球体外层和中层。
- 对后方粒子关闭 Hover。
- 使用屏幕空间距离辅助选择。
- 采用 GPU Picking 处理更高粒子数量。
- 在移动端用点击替代 Hover。

---

## 3.18 不应出现的效果

避免：

- 使用一张预渲染的球形图片。
- 所有点完全同步旋转。
- 所有粒子平均分布在标准球面。
- 球体内部完全实心。
- 所有标签始终显示。
- 大量标签同时出现。
- 粒子高速喷射。
- 密集固定连线。
- 过强霓虹和 bloom。
- 粒子一离开就突然消失。
- 右侧半球被持续吸空。
- Hover 时整个球体完全停止。
- 自动标签与 Hover 标签争夺显示状态。
- 使用过多颜色区分类别。
- 为每一个视觉粒子创建独立 DOM 节点。

---

## 3.19 左侧模型的最终产品语义

该球体不是地球、目的地或最终旅行计划。

它代表：

> 当前旅行小组中所有成员不断产生的个人想法、偏好、硬性约束和私密顾虑所共同形成的动态需求集合。

单个粒子强调独立性：

```text
一个粒子 = 一条独立想法
```

整个球体强调协作关系：

```text
所有粒子 = 当前团队共同需要被理解和协调的旅行需求
```

粒子被提取并进入中间平台，表达：

```text
分散需求
→ 被平台捕捉
→ 进入协调和处理阶段
```


# 4. 中间：产品处理区域暂时保留

## 4.1 当前设计结论

中间模型的最终概念暂时不定义。

现阶段不要提前决定它是：

- AI 大脑。
- 机器人。
- 魔方。
- 芯片。
- 水晶。
- 漩涡。
- 复杂机械平台。
- 带文字的流程模块。

这些形态都可能过早限制产品视觉语言。

---

## 4.2 当前阶段只保留结构接口

虽然中间概念空白，但为了让整体动画可以继续设计，仍需预留以下接口：

### 输入接口

- 接收左侧粒子。
- 位于中间区域偏左。
- 所有输入曲线在此收束。
- 粒子进入后消失或转化。
- 输入动作需要能触发中间区域未来的处理动画。

### 输出接口

- 位于中间区域偏右。
- 向右侧计划流程输出一个更稳定的激活信号。
- 输出可以是单个光点、光线、脉冲或其他形式。
- 最终表现方式待中间模型确定后再设计。

### 中间视觉占位

在原型阶段，可使用一个非常简单的无语义方块作为尺寸占位：

```text
┌───────────────┐
│               │
│   Placeholder │
│               │
└───────────────┘
```

但实际首页不显示 “Placeholder” 文字。

占位方块只用于确定：

- 中间模型的最大宽高。
- 左侧粒子汇聚位置。
- 右侧输出路径起点。
- 页面视觉重心。
- 响应式布局。

占位方块不代表最终产品符号，也不纳入品牌定义。

---

## 4.3 中间区域未来需要回答的问题

最终确定中间概念前，需要先回答：

1. 产品最核心的动作是“理解”“协调”“协商”还是“构建”？
2. 中间模型是否需要体现多人平等，而不是单向 AI 决策？
3. 它是否需要表达隐私保护？
4. 它是否需要表达硬性约束检查？
5. 它是否需要具备可重复使用的品牌识别度？
6. 它能否在导航栏图标、加载动画和产品 Logo 中复用？
7. 它是一个封闭黑盒，还是一个可看到内部变化的结构？
8. 输入和输出是否应保持同一种粒子语言，还是发生明显转换？

在这些问题明确前，中间区域保持概念空白是合理的。

---

# 5. 右侧：Plan Formation Flow

## 5.1 核心定义

右侧代表平台输出的结构化旅行方案。

它不是多个并列结果，也不是一次性全部出现的最终卡片。

它应呈现为：

> 一个自上而下逐步完成的计划流程。

初始状态下，所有节点与卡片均为无色或淡灰色。随着中间平台持续输出，流程从顶部开始逐层变为淡蓝色，表示计划正在形成。

---

## 5.2 结构形式

建议采用一条纵向主线和 5–6 个计划节点。

示意：

```text
        ○  Trip Foundation
        │
        ○  Stay
        │
        ○  Daily Activities
        │
        ○  Food & Transport
        │
        ○  Budget & Validation
        │
        ○  Final Shared Plan
```

正式视觉可以主要依靠图标和卡片结构，而不是大量文字。

建议阶段：

1. 旅行基础条件
2. 住宿方案
3. 每日活动
4. 餐饮与交通
5. 预算和可行性检查
6. 最终共同计划

这些节点对应产品实际需要生成的住宿、活动、餐饮、交通、路线和费用估算等计划组成部分。

---

## 5.3 初始状态

初始状态：

- 所有圆形节点为浅灰描边。
- 所有连接线为浅灰。
- 所有卡片为半透明或低对比度。
- 图标为浅灰色。
- 卡片内部只显示抽象占位结构，不显示复杂内容。

右侧整体看起来已经存在一个“计划骨架”，但尚未被填充。

---

## 5.4 自上而下的点亮机制

中间区域输出第一个信号后：

### 阶段 1：顶部节点激活

- 顶部节点从灰色变为淡蓝色。
- 节点出现短暂光环。
- 对应卡片边框和主要图标变蓝。
- 卡片内部内容从模糊占位变得清晰。

### 阶段 2：连接线向下填充

- 顶部节点下方的竖线从上向下变蓝。
- 动画像进度线流动，而不是整段突然变色。

### 阶段 3：下一个节点激活

- 第二节点点亮。
- 对应卡片开始形成。
- 然后继续向下推进。

该过程持续到最后一个节点。

---

## 5.5 “有色替代无色”的具体表现

不是在灰色节点上覆盖另一个蓝色节点，而是同一个组件在状态间过渡。

```text
inactive
→ receiving
→ active
→ confirmed
```

### inactive

- 灰色。
- 低对比度。
- 内容不可读或只保留骨架。

### receiving

- 节点周围出现淡蓝脉冲。
- 连线正在填充。
- 卡片轻微提升透明度。

### active

- 节点、连接线和卡片进入淡蓝主题。
- 卡片内容清晰。
- 保持稳定，不闪烁。

### confirmed

- 最终节点可以出现柔和对勾或完整环形。
- 不需要使用强烈绿色，继续保持品牌淡蓝色。

---

## 5.6 右侧动态节奏

建议每一层完成时间为 700–1,000ms。

完整流程可控制在 5–7 秒：

```text
0.0s  顶部节点开始激活
0.8s  第一层完成
1.1s  向下连接线填充
1.7s  第二层激活
2.6s  第三层激活
3.5s  第四层激活
4.4s  第五层激活
5.3s  最终节点激活
6.0s  完整计划保持展示
```

右侧动画应比左侧更稳定、更可预测，因为它代表秩序和结果。

---

## 5.7 右侧持续循环逻辑

Hero 动画可以循环，但不建议每次都把右侧完全重置为灰色。

推荐两种方案：

### 方案 A：首次完整播放，之后保持完成

适合真实产品首页：

- 用户首次进入时，从上到下点亮。
- 完成后保持完整计划。
- 左侧和中间仍继续轻微运动。
- 不重复清空右侧。

优点：结果稳定，不会让用户误以为计划一直被删除重建。

### 方案 B：柔和循环演示

适合概念演示页：

- 完整计划保持 3–5 秒。
- 所有节点逐渐降为低饱和状态。
- 不完全消失。
- 新一轮再次逐项点亮。

建议正式首页优先采用方案 A。

---

# 6. 左、中、右的整体动画关系

## 6.1 动画不是严格的一次性流水线

三个区域应同时存在活动：

- 左侧始终生成和漂浮粒子。
- 左侧始终有少量粒子被吸入。
- 中间区域未来持续响应输入。
- 右侧在首次进入时逐步形成计划。
- 右侧完成后保持稳定。

因此用户会看到：

```text
左边一直有新想法
        +
少量想法不断进入平台
        +
右边的计划逐步形成并最终稳定
```

---

## 6.2 推荐首次进入时间线

```text
0.0s  左侧 3D 球形想法模型淡入并开始缓慢运动
0.6s  第一组 1–3 个自动标签出现
1.2s  第一批粒子开始脱离模型
2.0s  粒子进入中间区域
2.3s  中间区域出现处理反馈
2.8s  右侧顶部节点开始激活
3.0s  左侧第二组自动标签出现
3.6s  第二批粒子进入中间
4.0s  右侧第二、第三节点继续形成
5.5s  右侧接近完成
6.5s  最终计划节点完成
7.0s+ 左侧继续持续生成与流动，右侧保持稳定
```

---

# 7. 颜色系统

## 7.1 主色

建议使用淡蓝作为唯一明确品牌色。

示例方向：

```text
Primary Pale Blue:     #9FC5FF
Soft Active Blue:      #6EA8FE
Light Blue Surface:    #EAF3FF
Very Light Blue:       #F5F9FF
Inactive Gray Blue:    #D8E0EA
Text Gray:             #6B7280
Background:            #FAFBFD
```

具体色值可在 UI 设计阶段再调整。

---

## 7.2 左侧颜色

- 普通点：极浅蓝和半透明白。
- 可交互点：稍深的淡蓝。
- 自动展示点：短暂提升亮度。
- 私密想法：不必使用红色，可使用带锁图标或略偏紫蓝的点。
- 被吸入点：逐渐变得更明亮。

避免通过大量不同颜色表示不同类别，否则左侧会失去统一感。

---

## 7.3 右侧颜色

- 未激活：灰蓝。
- 正在形成：中等淡蓝。
- 已完成：稳定淡蓝。
- 最终确认：可以使用蓝色对勾或完整蓝色圆环。
- 不建议使用绿色作为主要完成色，以保持品牌一致性。

---

# 8. 响应式设计

## 8.1 桌面端

展示完整三段式动画：

- 完整 3D 球形想法模型。
- 中间处理区。
- 右侧 5–6 层计划流程。
- 支持 Hover。
- 支持轻微鼠标视差。

---

## 8.2 平板端

- 降低粒子数量。
- 减少自动标签数量至 1–2 个。
- 缩小中间预留区域。
- 右侧保留 4–5 个核心节点。
- Hover 可保留，但需兼容点击。

---

## 8.3 移动端

不建议强行缩小整个横向动画。

推荐改为纵向叙事：

```text
3D 球形想法模型
      ↓
中间处理区
      ↓
计划逐步形成
```

移动端交互：

- 点击粒子显示标签。
- 点击空白区域关闭标签。
- 自动标签同一时间最多显示 1 个。
- 关闭鼠标视差。
- 降低 3D 粒子数量和后期效果。
- 右侧流程改为横向卡片或纵向时间线。

---

# 9. 性能与技术实现建议

## 9.1 左侧技术方向

优先考虑：

- Three.js
- React Three Fiber
- WebGL InstancedMesh
- GPU 粒子更新
- HTML overlay 或 CSS2DRenderer 标签

不要为每个点创建独立 DOM 元素。

推荐结构：

```text
WebGL Canvas
├── Instanced particle field
├── Interactive particle hit targets
├── Spline exit particles
├── Glow / depth effects
└── HTML tooltip overlay
```

---

## 9.2 Hover 检测

粒子数量较多时，不建议每一帧对所有粒子做复杂计算。

可考虑：

- Raycasting 只检测可交互粒子。
- 限制真正可 Hover 的粒子数量。
- 使用 spatial partition 或简化 hit target。
- 自动展示点与 Hover 点共用标签系统。

---

## 9.3 动效库

建议：

- Three.js / React Three Fiber：3D 粒子模型。
- GSAP：复杂时间线和路径动画。
- Framer Motion：DOM 标签和右侧 UI 状态过渡。
- SVG：右侧纵向流程线。
- CSS transitions：轻量 Hover 和卡片状态。

---

## 9.4 性能降级

应支持：

- 根据设备性能降低粒子数量。
- 低性能设备关闭 bloom。
- 页面不可见时暂停 WebGL 动画。
- `prefers-reduced-motion` 下关闭持续旋转和吸入动画。
- 移动端降低 DPR。
- 右侧流程仍应在无 3D 动画时正常展示。

---

# 10. 无障碍设计

- 所有想法点不应依赖颜色传递唯一含义。
- 自动标签不应快速闪烁。
- Hover 标签应支持键盘聚焦的替代方式。
- 标签文字需要足够对比度。
- `prefers-reduced-motion` 用户看到静态但可理解的版本。
- 3D 模型应标记为辅助视觉，不影响页面主要内容阅读。
- Hero 区域仍需要真正的 HTML 标题、副标题和 CTA，不能只依赖动画讲故事。

---

# 11. 当前阶段明确结论

## 已确定

### 左侧

- 是实时运行的 3D 球形想法模型，不是静态图片。
- 球体由大量独立粒子组成，并具有外层、中层和内层深度。
- 整体轮廓是球形，但粒子分布不规则，中心相对空旷。
- 每个可交互点都是独立想法实体。
- 每个可交互点可以 Hover 并显示标签。
- 标签不是始终可见。
- 系统每 2–3 秒自动展示 1–3 个标签。
- 标签会消失，并换成其他点。
- 球体整体缓慢旋转，单个粒子存在局部漂移。
- 新点不断从外围、后方和内部淡入。
- 少量粒子不断从右侧脱离并进入中间平台。
- 粒子流出后会在其他区域补充，球体不会被吸空。
- 整体使用淡蓝、蓝白和灰蓝色层级。
- 视觉上学习球形粒子信息体的机制，但不复制参考网站的素材或源码。

### 右侧

- 是自上而下的计划形成流程。
- 初始状态为灰色或无色。
- 节点、连线和卡片逐层变为淡蓝色。
- 表示计划逐步构建完成。
- 完成后优先保持稳定状态。

---

## 尚未确定

### 中间

- 最终产品符号。
- 具体 3D 形态。
- 是否使用方块、平台、晶体、网络或其他形式。
- 输入粒子在内部如何转化。
- 输出信号的具体样式。
- 是否可以发展为品牌 Logo 或加载动画。

当前只保留中间区域的尺寸、输入接口和输出接口。

# 12. 第一阶段原型验收标准

左侧原型完成后，应满足：

1. 页面中存在真正由 WebGL 渲染的 3D 球形粒子模型，而不是静态图。
2. 球体具有清晰轮廓、内部厚度和前后深度。
3. 粒子分布不规则，中心区域相对空旷，外围轮廓更明确。
4. 球体整体缓慢旋转，单个粒子同时存在轻微局部漂移。
5. 桌面端可以根据设备性能显示至少 1,500 个视觉粒子。
6. 至少有一组独立的可交互想法粒子。
7. 用户可以 Hover 可交互粒子。
8. Hover 后显示与该粒子绑定的标签。
9. 鼠标移开后标签自然淡出。
10. 系统能每 2–3 秒自动展示 1–3 个随机标签。
11. 自动标签不会始终固定显示。
12. 自动展示不会选择被遮挡严重或位于球体后方的粒子。
13. 新粒子会从球体外围、后方或内部持续淡入。
14. 粒子会以 1–4 个的小批次从右侧脱离球体。
15. 粒子脱离前存在可观察的选择和分离过程。
16. 粒子沿 3D 曲线路径进入中间区域。
17. 曲线路径平时不可见，只在粒子经过时显示局部光迹。
18. 粒子离开后，系统会在其他区域补充新粒子。
19. 球体总体半径和视觉密度保持稳定。
20. 被 Hover 的粒子不会在交互过程中被吸走。
21. 动画在普通桌面设备上没有明显卡顿。
22. 在低性能设备和 reduced-motion 环境下可以降级。

右侧原型完成后，应满足：

1. 初始所有节点均为灰色。
2. 流程可以自上而下逐层激活。
3. 连线呈现真实的向下填充过程。
4. 对应卡片和图标随节点一起变为淡蓝色。
5. 最终节点清楚表达完整计划已经形成。
6. 正式首页中完成后保持稳定，不反复清空。

---

# 13. 下一步设计任务

建议后续按以下顺序推进：

1. 为左侧 3D 球形模型建立低保真交互原型。
2. 确定球体半径、球壳厚度、粒子密度、旋转速度和 Hover 手感。
3. 测试自动标签出现频率是否干扰阅读。
4. 建立右侧纵向计划流程的 UI 原型。
5. 确认首页整体比例和响应式布局。
6. 再单独探索中间产品符号。
7. 最后统一输入、处理和输出的动画节奏。

中间模型应作为独立设计课题处理，不应在左侧和右侧尚未验证前被仓促定型。
